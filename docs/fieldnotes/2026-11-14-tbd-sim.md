# 2026-11-14 — TBD physics sim, game step and wasm binding

*By Starscream, Engine Lead.*

**What:** TBD, a physics sim with estimated parameters, now has a game step in the repo. TBD is the working name. The MuJoCo model was already in `assets/tbd/`. This adds the Rust side of the architecture in `assets/tbd/reference/ARCH.md`.

- **`games/tbd`.** Pure Rust, no MuJoCo. Cascade flight controller (position and velocity PD, attitude PD, X mixer), battery model, mode machine (ground, unfolding, flight, landing, folding), stair-hop mission with a timer and a score, and wind drawn from a ChaCha8 stream seeded the same way as the engine RNG. One tick is 20 floats in and 9 actuator commands out, in `tbd.xml` sensor and actuator order. Unit tests include a tolerance check against the Python and JS reference controller on fixed inputs.
- **`WasmTbd`.** `new(seed, configJson)`, `step(obs)`, `stateJson()`, `reset()`, in the committed `web/pkg`. The page that owns MuJoCo WASM and three.js calls `step` once per physics tick and applies `wind_force_n` itself. That page is not in this change.
- **`tbd-native`.** Optional. `cargo test` does not link MuJoCo. With `--features native`, mujoco-rs 7.1 (MuJoCo 3.17) loads `assets/tbd/tbd.xml` and runs the stair hop. The model file and the browser build are MuJoCo 4.0.1. A seed-1 hop on 3.17 completed, landed, and scored.
- **Notices.** `THIRD_PARTY_NOTICES.md` credits MuJoCo (Apache-2.0, Google DeepMind), three.js (MIT) and mujoco-rs.

**Why:** So the browser page can swap its JS controller for the same Rust step the native runner uses, without putting MuJoCo inside the tank and racing wasm.

**Verified:** `cargo test -p tbd` (controller parity and the scripted stair hop). Native feature: a 0.2 s determinism test, and a full stair hop (`completed`, `landed_on_landing`). `web/pkg` rebuilt with `scripts/build-wasm.sh`. `engine_wasm_bg.wasm` went from 418,704 bytes to 483,488 (177,868 gzipped at `-9 -n`).
